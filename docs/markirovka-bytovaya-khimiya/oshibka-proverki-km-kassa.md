# Ошибка проверки КМ на кассе

Сообщение «Ошибка проверки КМ, маркировка будет отвергнута» здесь из‑за **несовпадения типа**: в ошибке ПО **по умолчанию приписывает короткий КМ**, а на кассу **приходит полный**. ФН видит не тот шаблон и возвращает ошибку кодирования. Продавать единицу как остаток нельзя.

## В чём причина

ФН проверяет код **по типу, который ему сказали**, а не «как на упаковке». ПО для этой группы ставит короткий тип (`MarkingType2 3`, шаблон AI 93). Сканер отдаёт полный КМ (хвост `91`/`92`). ФН пытается разобрать полный буфер как короткий — `CheckItemLocalError 1`, проверка не выполняется. 1С строку не снимает, в чек всё равно идёт М.

Откуда берётся короткий тип по умолчанию:

| Где | Что обычно стоит |
| --- | --- |
| Вид продукции ИС / карточка | Шаблон кодов «короткий» для косметики и бытовой химии |
| РМК / обработка проверки КМ | Тип КМ не смотрят по факту скана, берут с карточки |
| Текст ошибки | Печатают КИ / printView без хвоста — поэтому в дампе короткий кусок |

Полный КМ на этой группе законный: так часто маркирует производитель или импортёр. GTIN `05413048311093` с префиксом 541 — как раз импорт. Учёт при этом мог быть заведён под короткие коды СУЗ.

Это **не** причина:

- нет связи с «Честным знаком» — `KMServer* -1` потому что до онлайн-проверки не дошли (локально уже ошибка формата, плюс разрешительный режим с 01.04.2027);
- законный остаток без маркировки — Data Matrix есть, в чеке М;
- «криптохвост отвалился на сканере» — на кассу приходит полный код.

## Этот дамп

```
Ошибка проверки КМ, маркировка будет отвергнута.
Необходимо уведомить бухгалтера
0105413048311093215BTLoSntrqS?
"0 Ошибок нет"
CheckItemLocalResult 0
CheckItemLocalError 1
MarkingType2 3
KMServerErrorCode -1
KMServerCheckingStatus -1
```

| Поле | Значение | Что это |
| --- | --- | --- |
| КМ в тексте ошибки | `0105413048311093215BTLoSntrqS?` | Короткий фрагмент / КИ без хвоста. Так ошибка **подписывает** код по умолчанию |
| Что пришло на ККТ | полный КМ | `01` + GTIN + `21` + серийник 6 + GS + `91` + 4 + GS + `92` + 44 |
| `Ошибок нет` | код 0 драйвера | Команда до кассы дошла. Это не «КМ хороший» |
| CheckItemLocalResult | 0 | ФН **не смог** проверить код проверки: ждал короткий шаблон |
| CheckItemLocalError | 1 | Некорректный формат относительно **приписанного** короткого типа |
| MarkingType2 | 3 | Касса пометила КМ как **короткий**. Для полного нужен тип полного КМ (2 или 4), не 3 |
| KMServer* | -1 / -1 | Онлайн-проверка не вызывалась |
| В чеке | **М** | Позиция ушла как маркированная. Это не успех проверки |

При «маркировка будет отвергнута» 1С **не выкидывает** строку: КМ всё равно попадает в фискальный документ. На печати это **М** или **[М-]**, не **[М+]**. LocalResult 0 и LocalError 1 значат: ФН код не принял. Буква М в чеке ≠ вывод в «Честный знак». Код может остаться в обороте.

С 01.07.2026 маркированную бытовую химию выводят через кассу. До 01.04.2027 касса ещё даёт закрыть такой чек. Закрытый чек с М при этой ошибке — повод для бухгалтера, а не «всё хорошо».

## Два законных формата, тип берётся со скана

Для косметики и бытовой химии серийник **ровно 6 символов**. Между серийником и хвостом — **GS, ASCII 29**.

| Вид | Структура | Какой тип слать в ККТ |
| --- | --- | --- |
| Короткий | `01` + GTIN 14 + `21` + серийник 6 + GS + `93` + 4 | короткий (AI 93) |
| Полный | `01` + GTIN 14 + `21` + серийник 6 + GS + `91` + 4 + GS + `92` + 44 | полный (AI 91/92) |

Оба выпускает «Честный знак». На карточке и в РМК **нельзя** зашить «всегда короткий». Тип смотрит сам скан: есть `93` — короткий, есть `91`/`92` — полный. Полный код в ККТ уходит **как пришёл**, без обрезки хвоста.

В дампе в ошибку попал короткий кусок. Кавычка в полном КМ (допустимый символ хвоста) обрывает текст сообщения. Смотреть нужно не на этот фрагмент, а на то, что сканер отдал в ККТ.

## Что сделать в ПО

1. Не ставить шаблон «короткий КМ» по умолчанию на группу косметика / бытовая химия.
2. После скана определить вид по AI: `93` → короткий, `91`+`92` → полный.
3. В ФН уходит тот же буфер, что пришёл со сканера, плюс тип **этого** буфера. Полный не превращать в короткий printView / КИ.
4. `MarkingType2` для полного — не 3. Если пришёл полный, а тип 3 — это и есть данный сбой.
5. В текст ошибки писать полный КМ с GS как `<GS>`, не обрезать на `"`.
6. Если проверка не прошла, в чеке не рисовать успех: печать **М** / **[М-]**, не **[М+]**. Буква М в UI не значит «КМ принят».

## Что делать на кассе

1. **Не** менять строку на артикул-остаток. Data Matrix есть — это маркированный двойник. М в чеке это подтверждает: товар пошёл как маркированный.
2. Если чек **ещё не закрыт** — не пробивать, пока КМ отвергнут. Повторить скан той же единицы.
3. Если чек **уже закрыт и в нём М** — не бить повторно. Отложить такую же единицу с полки не нужно: она уже в чеке. Звать бухгалтера и IT.
4. Если повтор скана до закрытия сразу проходит (LocalError 0 и Result 1, в чеке будет М+) — оставить артикул-М.

```
Повтор не прошёл
        │
        ▼
В ошибке короткий тип, на ФН полный КМ?
        │
        ├─ Да  → снять шаблон «короткий».
        │        Передать полный КМ как полный.
        │        Не резать хвост 91/92.
        │
        └─ Нет → смотреть GS и сам код
                  │
                  ├─ Нет GS → настроить сканер на ASCII 29
                  └─ GS на месте → проверить КМ в Честном знаке
                        │
                        ├─ Код наш и в обороте → отложить, IT
                        └─ Кода нет / чужой     → карантин, бухгалтер
```

## Кто что делает

| Роль | Действие |
| --- | --- |
| Кассир | Не подменять остатком. Не закрытый чек — повторный скан. Уже есть М в чеке — не бить второй раз, позвать бухгалтера |
| IT | Снять умолчание «короткий КМ». Тип с факта скана. Полный буфер на ФН. Не ставить М+ при LocalError 1 |
| Бухгалтер | Чек с М при этой ошибке сверить с ЧЗ и ОФД. Код мог не выйти из оборота. Корректировка или возврат, не оставлять как успешный вывод |
